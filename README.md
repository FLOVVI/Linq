# LinQ — система видеоконтроля промбезопасности

Монорепозиторий: в корне — бэкенд (`main.py`, `db.py`, FastAPI), схема PostgreSQL (`schema.sql`) и `docker-compose.yml`;
`frontend/` (React + Vite); `ai/` — ИИ-модуль (распознавание нарушений на видео, LinQ TPU / ONNX), подробности в [ai/AI.md](ai/AI.md).

## Запуск
1. БД: `docker compose up -d` (PostgreSQL, схема из `schema.sql` применяется сама; строка подключения — `DATABASE_URL` в `.env`).
2. Бэкенд: `pip install -r requirements.txt && uvicorn main:app --reload` (порт 8000, Swagger: `/docs`).
   При первом запуске создаются демо-пользователи и 3 камеры. Логины: `mikhalyich_ot` (роль 1), `disp_smena1` (3), `master_ceh1` (2), `it_linq_admin` (7); пароль `linq123` (env `SEED_PASSWORD`).
3. Фронтенд: `cd frontend && npm install && npm run dev` → http://127.0.0.1:5173 (запросы `/api/*` проксируются на бэкенд; для другого адреса — `VITE_API_URL`).

4. ИИ-модуль (папка `ai/`: код, модели, тестовые видео):
   зависимости те же, что в корневом `requirements.txt` (`python -m venv .venv && .venv/bin/pip install -r requirements.txt`), затем
   `cd ai && ../.venv/bin/python -m safetyvision bridge configs/site_bridge.yaml` (на ускорителе LinQ — `--backend tpu`). Он берёт с сайта камеры, правила и зоны, анализирует видео и присылает
   нарушения; живое видео с разметкой отдаёт на порту 8001. Без него сайт работает, но в журнале только тестовые инциденты.

## ИИ-модуль ↔ сайт
- **Камеры.** Источник видео — `rtsp_url` камеры (RTSP/HTTP, номер веб-камеры или путь к файлу) либо видео, загруженное
  кнопкой «Видеофайл» (`PUT /cameras/{id}/video`, файл в `uploads/videos`). Для демо `ai/configs/site_bridge.yaml`
  (секция `sources`) подставляет камерам CAM-01…03 записи с завода; зацикленная запись не дублирует события.
- **Правила.** Вектор из 13 позиций: 01–08 — прежние паттерны, 09–13 — СИЗ и опасная зона (`NO_HELMET`, `NO_VEST`,
  `DANGER_ZONE`, `NO_GLOVES`, `NO_GOGGLES`). У 05, 06, 08 у ИИ пока нет детектора — в матрице правил это отмечено.
  Старые векторы из 8 чисел дополняются автоматически (каска, жилет, опасная зона — включены).
- **Зоны** рисуются на живом кадре в процентах кадра. Опасная — вход в неё нарушение (если включён тип 11),
  «Особое внимание» — обязательны каска и жилет, «Слепая» — участок кадра не контролируется. Расписание зоны работает.
- **События.** Начало приходит сразу (`POST /events`: тип, камера, зона, стоп-кадр, миникарта, точка на плане), конец —
  когда нарушение закончилось (`PATCH /events/{id}/ai`: `ended_at`, длительность, видеоклип). Один инцидент — одно событие.
- **Статус** камер (FPS, задержка, бэкенд ONNX/LinQ TPU, адрес видеопотока) — `PUT /ai/cameras/{id}/status` раз в 3 с,
  хранится в памяти бэкенда; без ИИ-модуля сайт честно пишет «не в сети», а не выдуманные 96 FPS.
- **Обратная связь.** «Подтвердить» / «Ложное» попадают в набор для дообучения ИИ-модуля (`ai/runs/site_bridge/*/review`),
  кнопка «Выгрузить выборку для дообучения» скачивает архив кадров и клипов ложных срабатываний.
- Служебные методы ИИ-модуля (`/ai/*`, `PATCH /events/{id}/ai`) требуют `X-Api-Key` = `INGEST_KEY`.

## Как связано
- Интерфейс показывает экран входа, затем загружает камеры, события, настройки и статистику с API.
- Правила, зоны, PTZ и позиции камер сохраняются автоматически (через 0.6 с), при отказе по правам — откат. Журнал инцидентов опрашивает `/events?since_id=` каждые 5 с. Реакция на событие (подтвердить / мастеру / ложная) и комментарий пишутся в БД. «Тестовый инцидент» создаёт событие через `POST /events`.
- AI-сервис присылает нарушения на `POST /events` с заголовком `X-Api-Key` (env `INGEST_KEY`, по умолчанию `dev-ingest-key`).
- Права: просмотр — роли 1,2,3,7; правка камер/зон/правил/настроек/пользователей — 1 и 7; реакция на события — 1,2,3; PTZ — любой.

## Изменения в схеме БД
В `cameras` добавлена колонка `extra jsonb` (наклон PTZ, программа TPU, объекты симуляции — поля интерфейса без своих колонок).
Для ИИ-модуля: в `violation_type` добавлены 5 значений (09–13), в `events` — `ended_at`, `duration_s`, `clip_url`, `zone`,
`ai_event_id` (уникальный); в `sessions` — `expires_at` (его уже использовал `db.py`, а в `schema.sql` колонки не было,
и вход падал). Бэкенд при старте сам доводит существующую БД до этой схемы (`ALTER ... IF NOT EXISTS`).
Строка подключения в `.env` исправлена на порт 5433 — тот, что открывает `docker-compose.yml`.
Описание контракта слоя БД — `db.py` (весь SQL только там), заметки — `DB_TASKS.md`.
